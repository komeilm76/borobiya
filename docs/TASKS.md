### 4.1 Search & Geocoding

- [ ] **T4.1.1** `GET /_user/users/search?q&category&incidentType&minRating&sort=distance` + pagination, debounced 300ms, autocomplete
  - **Partial (server read, 2026-10-22):** the endpoint is registered and answers a term-bounded search, pulled forward as the location-share picker's dependency. `q` (≥2 chars, case-insensitive partial username match, `LIKE` wildcards escaped) over accounts a share can actually reach; `minRating` (unrated = 0) and `online` (a session still holding a refresh token, the same rule as the device list) are honored; `distance` is kilometres to `lat`/`lon` or the caller's last stored position, positionless accounts sorted last; shared pagination bounds apply, with the total counted in its own statement so an out-of-range page still reports it. `category`/`incidentType` return `400 SEARCH_FILTER_UNSUPPORTED` instead of being ignored, because the domain tables do not exist yet. Still open here: term-free browsing with an index to back it (no trigram/prefix index on `users.username` yet), category/incident filters and radius limits (the client's debounced autocomplete landed with T2.1.7). **Fixed 2026-10-22 after the first live run:** the projection used `round(ST_Distance(...) / 1000.0, 1)`, but PostgreSQL has no two-argument `round` for `double precision`, so every search was a 500; it is now `round((...) / 1000.0)::numeric, 1)::float8`, with `readDistanceKm` keeping a `NULL` distance instead of turning it into 0 km. The escaped `ILIKE` pattern, the rating floor, the `exists` liveness check, the `NULLS LAST` ordering, and `count(*)::int` were then executed against a real PostgreSQL via PGlite (no PostGIS there), which is also how the bug was confirmed rather than guessed.
