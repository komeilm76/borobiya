# Legacy architecture review

The previous repository was a large multi-package system. The visible portions included a Fastify server with TypeScript, PostgreSQL and PostGIS, Socket.IO, OpenAPI tooling and roughly forty store and route registrations; a Vue, Vuetify, Tailwind, Vite, Pinia, VueUse and MapLibre client; an Ionic and Capacitor Android application; an independent offline MVT map server; twenty-one Drizzle migrations; and separate admin and map design trees. The original code review was partial before the clean rebuild. A later targeted review of the legacy `README.md`, `docs/TASKS.md`, `docs/ROADMAP.md` and `docs/PROGRESS.md` reconciled the old target families with the clean architecture; this document records structural and scope conclusions rather than claiming a complete line-by-line code audit.

## Problems addressed

The old architecture duplicated concepts across packages: API groups, client stores, realtime rooms, map caches, theme definitions, status values and test fixtures. Runtime work was spread across a web server, a map server, a database server and several build toolchains. This made a local clean start expensive and made it difficult to prove that an SOS transition, a socket event and an administrator table were driven by one state machine.

The Bun/Vue rebuild replaces that with one Bun process, one SQLite schema, one declarative route table, one service layer, one WebSocket endpoint, one shared protocol module and one browser application. Pure geometry and state rules are centralized. Offline map tiles are deterministic SVG generated in-process rather than a separate MVT service. Static assets are generated by one script and precached by one service worker.

## What was retained

The canonical images, reference generators, icon inventory and theme files under `design/` were retained as the visual contract. The product remains right-to-left, keeps system/light/dark themes, preserves the mobile map as the primary surface, and keeps administrator concepts such as overview, dispatch, users, groups, reports, audit, alerts and settings. The SOS and mission workflows, press-and-hold talk, live location, history playback and saved places remain first-class features.

Stable demo identifiers were recreated in a compact catalog so deterministic tests can exercise registration, recovery, dispatch, sharing and mission completion. Hardcoded demo credentials remain outside production seeding. The old idea of durable events and audience-filtered catch-up was retained but simplified into one SQLite event table and one post-commit publisher.

## What was discarded

The old multi-package layout, ORM migrations, Docker and proxy files from the old deployment, old Python design tests and legacy documentation were removed. Its web stack was later deliberately reinstated as the current implementation: Vue 3, Vuetify 3, Tailwind CSS 4, Pinia, VueUse and Vite now run on Bun, so 2.0.0 keeps those framework-specific stores and plugin chains while dropping the Node runtime and duplicate manifests. The deletions are committed in the clean-rebuild commit `e1a7e91`; a reviewer can inspect previous files from its parent, for example `git show e1a7e91^:docs/TASKS.md`, without affecting the new implementation. `HEAD` is the clean rebuild, not the legacy tree.

All old tests and manuals were replaced by new English documentation and a new Vitest suite executed under Bun. The new tests cover pure rules, API contracts, authentication, security, realtime coordination, PTT binary frames, live location, complete journeys, architecture boundaries, generated assets, accessibility, performance and acceptance invariants. This makes the rebuilt system verifiable from a clean checkout with one install and one check command.

## Scope reconciliation

The legacy root README marked an independent map server, offline geocoding, professional multi-destination routing, navigation camera modes, an Android application, Dockerized Ubuntu deployment and Windows development as mandatory. Those requirements belonged to the discarded multi-service architecture. `docs/ACCEPTANCE.md` now names them explicitly as superseded by one responsive browser application, deterministic in-process SVG tiles, a simplified SOS-to-mission workflow, Bun-only startup, CI gates and the new operations runbook.

The legacy `ROADMAP.md` also listed unshipped geocoding, skeletons, virtual scroll, Playwright acceptance, Lefthook/Husky hooks, deploy workflows and screenshot/diagram sign-off. The clean rebuild supplies its own equivalents where still relevant: loading/offline/error surfaces, lazy view imports, automated contrast checks, a full login-to-rating API/realtime journey, Bun-native benchmarks, CI verification and practical English docs. `PROGRESS.md` had no open checkboxes and functioned as a dated work log, so its many later UI follow-ups are not carried forward as new acceptance obligations. Professional visual comparison against the canonical PNG references remains a separate human review.
