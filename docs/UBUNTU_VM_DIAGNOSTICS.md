# VM diagnostics (launch and after launch)

Start with **`python3 scripts/vm.py doctor`** from the repo root. It changes nothing, prints no secrets and checks configuration, Docker, browser build, local HTTP paths and application Postgres authentication via a read-only `SELECT 1` over the Compose network. If it fails, use the first failing row below, make **one** repair, and repeat. `doctor` does not verify migrations or application data operations, and its public HTTPS probe runs only from the VM (which may lack NAT hairpin); an external browser/GPS test is still required. Prefer `python3 scripts/vm.py launch` for safe stage resumption over deleting artifacts. The full [runbook §9](./UBUNTU_VM_RUNBOOK.md#9-troubleshooting-index) covers stage-specific recovery.

| Symptom / failing check | Safe next action |
| --- | --- |
| Tool missing/incompatible | `./scripts/vm-install.sh --check`; use `--install` on Ubuntu 24.04. Java ≥21, Osmium **exactly** the `.env` pin, Compose plugin v2 or newer, Bun exactly `package.json`. Docker group changes need a **new login**. |
| `vm-env.py` stops after the mode prompt with `could not identify Compose project` / exit 125 | **This failed run did not write new credentials to `.env`.** The script must identify this project's existing DB volumes before generating passwords; it cannot safely guess. Run `./scripts/vm-install.sh --check`: if Docker Engine and daemon are OK but Compose is missing, run `./scripts/vm-install.sh --install-compose` (matches your installed apt package family; never replaces the engine). Otherwise check `docker compose version`, `docker info` and `docker compose config --quiet` **locally**. `config --quiet` returning zero but `config --format json` failing suggests an incompatible Compose plugin. Fix the failing check, then rerun `vm-env.py`; never delete volumes to make the error disappear. Do not share rendered Compose config or `.env`. |
| Compose plugin missing and `apt-get update` says `.../ubuntu VERSION_CODENAME=noble Release` (404) | An older runbook command wrote the assignment instead of its value into the Docker APT source. Follow [runbook §A2's exact-line repair](./UBUNTU_VM_RUNBOOK.md#a2-docker-engine--compose-v2-from-the-official-docker-repository) to back up and replace **only** that malformed suite with `noble`; rerun `./scripts/vm-install.sh --install-compose`. Do not reinstall Docker or disable APT signature checks. |
| `apt-get update` warns `NO_PUBKEY 7EA0A9C3F273FCD8` for Docker | Inspect the active Docker APT source **locally** and its `signed-by` path. If it says `docker.gpg` but only `docker.asc` exists, follow [runbook §A2's guarded source/key repair](./UBUNTU_VM_RUNBOOK.md#a2-docker-engine--compose-v2-from-the-official-docker-repository). Otherwise retrieve Docker's official key from `https://download.docker.com/linux/ubuntu/gpg` and install it **at the path the source names**, `.asc` armored or `.gpg` dearmored. Never use `trusted=yes`, `apt-key`, or `--allow-unauthenticated`. Plain `apt-get update` may return success while reusing stale indexes; `./scripts/vm-install.sh --install-compose` uses `APT::Update::Error-Mode=any` and must succeed before installing the plugin. |
| `vm-env.py` cannot list `postgres-data`, or `docker info` says permission denied at `/var/run/docker.sock` | The writer checks volumes **before** prompting for mode/password and does not write new credentials on this failure. Run `./scripts/vm-install.sh --check`; if tools are OK but only socket access fails, run `./scripts/vm-install.sh --enable-docker-access` as your normal user. After its explicit root-equivalent group grant, **reconnect SSH or run `newgrp docker` in your terminal** (use a new tmux session); a script cannot change its parent shell's groups. Confirm `docker info` and `./scripts/vm-install.sh --check` succeed in that session, then rerun `vm-env.py`, finish its prompts, and only then launch. Do not use `sudo` on the Python scripts, reinstall Docker, regenerate passwords by hand or remove volumes. |
| `vm-install.sh --check` says `Docker volume inspection UNAVAILABLE` despite `Docker daemon access OK` | `docker info` alone does not prove that `vm-env.py` may list volumes. Run `docker volume ls -q --filter label=com.docker.compose.volume=postgres-data` **locally** to see the error; fix volume-list permissions/daemon policy before running `vm-env.py`. Do not generate credentials over an unverified volume, use `sudo` on the Python scripts, or reinstall Docker just for this failure. |
| Docker daemon unreachable for other reasons | Check `docker info` and `systemctl status docker` **locally**, then socket owner/group via `stat -c '%A %U:%G %n' /var/run/docker.sock`. If group access is already effective but the daemon is down, repair the service rather than changing permissions; check disk/inodes via `df -h` / `df -i`. Do not prune other projects' volumes. |
| Compose invalid or subnet conflict | `docker compose -f docker-compose.yml -f docker-compose.vm.yml -f docker-compose.production.yml --profile production config --quiet`; inspect port/subnet conflicts. If changing the pinned network `172.30.0.0/24`, also change `TRUSTED_PROXY_IPS` (see long runbook). Do not post full `compose config` (it includes credentials). |
| Database unhealthy / auth error `28P01` | `docker compose ps postgres`; `.env` password, container environment and volume role must agree. Restore the *original* volume password or use [runbook §9.3](./UBUNTU_VM_RUNBOOK.md#93-step-12-containers) for the interactive role-recovery probe; `vm.py launch` intentionally cannot approve a password change. Never print `docker inspect` secrets, regenerate a password over a populated volume or `down -v`. Back up with `python3 scripts/vm.py backup /safe/place/new.dump` before any deliberate deletion. |
| `GET /health` succeeds but `GET /api/_public/health` fails | `/health` only tests Nginx; API health proves the API process, **not database queries** (`doctor` runs its Postgres `SELECT 1` separately). Check `docker compose ps api postgres`; then `docker compose logs --tail 40 api postgres` **locally** (logs might contain sensitive data). Re-run launch for migration/seed; do not truncate the database. |
| `/map-config` fails, tiles/routing/geocoding missing | `docker compose --profile routing --profile geocoding ps`; verify `.env` map selection and library paths. `./map-server/scripts/verify-tiles.sh AREA`, `verify-routing.sh AREA`, `verify-geocoding.sh AREA`; rerun `python3 scripts/vm.py launch` to rebuild missing artifacts. `.env` + `current.json` must describe the same selection. |
| Geofabrik `iran-261018.osm.pbf` (or another dated extract) returns HTTP 404 | An HTTP response is not proof that your proxy is broken: the repository's pinned date can age out, **or** a proxy can return its own 404. In the same shell as `launch`, compare headers without downloading the PBF: `curl -sSIL --connect-timeout 8 --max-time 20 -o /dev/null -w 'pinned HTTP=%{http_code}\n' https://download.geofabrik.de/asia/iran-261018.osm.pbf` and repeat for `https://download.geofabrik.de/asia/iran-latest.osm.pbf` (diagnostic only; do not build from a moving `-latest` URL). On `python3 scripts/vm.py launch` with `cache-first`, the setup preflight automatically tries the latest common dated snapshot when the requested dated PBF or MD5 sidecar returns 404/410. It skips dates already found unavailable, verifies downloaded bytes against trusted MD5s, and only updates the saved `.vm-map.json` date after full setup succeeds (`.env` may already contain the staged date). To deliberately update a still-available date, run `python3 scripts/vm-map.py --snapshot latest --policy cache-first` and then `launch`. If both fail or HEAD and GET disagree, investigate proxy/host responses locally; a proxy-generated 404 is possible. Do not edit only `.env`, disable TLS checks, delete volumes, or edit catalog checksums. |
| `regions: snapshot must use YYYY-MM-DD, got 'date'` after `Merging …` | An older `prepare-regions-pbf.sh` passed its internal `date` mode as a `--snapshot` spec when writing provenance. Use a checkout containing the manifest handoff fix (check `git log -1 --oneline` in that checkout), then rerun `python3 scripts/vm.py launch`. To reuse the **same dated extract** if your pending `latest` selection might resolve to a newer date, first run `python3 scripts/vm-map.py --snapshot 2026-10-26 --policy cache-first` (replace the date with the one in **your** failed run; this keeps your existing area and library selection). The retry verifies the cached extract's trusted MD5 and re-merges; an unmanifested merged PBF is reused only if byte-identical to the fresh merge. A mismatch stops without replacing it; inspect it before considering the explicit `MAP_CROP_OVERWRITE=1` override. This failure happened before browser/DB/HTTP startup, so `doctor` may report those missing. Do **not** remove source downloads, `.env`, or Docker volumes; do not run `clear-caches`, `destroy`, or `down -v` to fix a manifest error. |
| Cached Geofabrik PBF has a mismatched MD5 or size | `cache-first` now retries the same dated extract into staging and only replaces the corrupt copy after the downloaded bytes match the trusted checksum. If the download fails, the old copy remains for inspection; a downloaded checksum mismatch is a hard stop, not permission to choose a different snapshot. `offline` does not retry online. Do not delete a verified extract or modify catalog checksums. |
| Geofabrik download times out after enabling the proxy | APT/Docker proxy settings do **not** update the shell that started `vm.py`. In **that interactive Bash shell**, run `source ~/.bashrc` to reload proxy exports (or open a new SSH terminal); **do not** reset/delete maps or Docker volumes. Verify `https_proxy`/`HTTPS_PROXY` is set without printing its value: `printf 'https_proxy=%s HTTPS_PROXY=%s\n' "${https_proxy:+set}" "${HTTPS_PROXY:+set}"`. Then test `curl -sSI --connect-timeout 8 --max-time 20 -o /dev/null -w 'HTTP=%{http_code}\n' https://download.geofabrik.de/` before restarting launch **from the same shell**. If it fails, compare with `no_proxy= NO_PROXY= curl ...` per [runbook §5.2](./UBUNTU_VM_RUNBOOK.md#52-verify-that-the-proxy-itself-works). Never paste proxy URLs or verbose curl output (they may contain passwords); do not disable certificate verification. |
| Photon import failed or ran out of disk | Check `df -h` **both** Docker storage and map library; `docker compose --profile geocoding-import logs --tail 40 nominatim`. Initial import can take about an hour. A failed Photon index is **not** a reason to remove the application `postgres-data` volume. |
| Browser `/` gives gateway text/404, or no MapLibre worker | A host-side `OK browser build files` does not prove Nginx mounted it. If `/` returns the **base gateway text**, use the read-only checks and Nginx-only recovery below. For a missing host build or worker, run `python3 scripts/vm.py launch` to build the UI; `--serve-only` refuses an absent build. |
| TLS edge / public HTTPS fails | Confirm `PUBLIC_DOMAIN`, A/AAAA records point to this VM, public TCP 80/443 reach Caddy, no other service owns those ports, and certificate issuance has Internet access. `docker compose -f docker-compose.yml -f docker-compose.vm.yml -f docker-compose.production.yml --profile production logs --tail 40 edge` locally; redact before sharing. The VM's own HTTPS probe may warn due to NAT hairpin; check from an external browser. |
| Login works but browser location is blocked | Production must be visited over Caddy's HTTPS origin; remote plain HTTP is not a secure browser context. Development: SSH-tunnel `5173` (HMR) or `8080` (built UI) to localhost. |
| Offline restart fails | Pre-cache all Docker images, source/reference files, Photon/Planetiler JARs, compiled UI and active dataset online. Use `python3 scripts/vm.py launch --serve-only` after `stop`; this command never pulls or builds. An unresolved `latest`, a `pinned` selection whose active date is not the repository pin, or a disagreement among the saved selection, `.env` snapshot and `MAP_DATA_VERSION` is refused until full launch fixes it; `doctor` warns about the mismatch. The active `current.json` must be a JSON object matching the selected date, dataset and numeric `MAP_BBOX`; a stale bbox would advertise the wrong map bounds. `--serve-only` refuses symlinked library paths and artifacts rather than following them outside the configured library. Successful setup saves its resolved date to `.vm-map.json`. The full `--offline` build forbids online map sources but can still need Docker/npm build dependencies. |
| Port 8080 not responding | `docker compose -f docker-compose.yml -f docker-compose.vm.yml --profile routing --profile geocoding ps`; check `NGINX_PORT`, `ss -ltn`, and container health. The development gateway binds loopback; use an SSH tunnel or production Caddy HTTPS. |

### Browser root serves the base gateway instead of the built app

`GET /health`, `/api/_public/health` and `/map-config` can all succeed with the **base**
`nginx.conf`, whose `/` returns `Borobiya API/map gateway…` as plain text. `doctor` checks that
`dist/index.html` exists **on the host**, not that the running Nginx container mounted it. This can
happen if Nginx was started/recreated using only `docker-compose.yml` after a VM launch; do not
reset the DB or map library. On the VM, from `~/borobiya`, check only the effective config/mount
(no secrets or response bodies are printed):

```bash
docker compose -f docker-compose.yml -f docker-compose.vm.yml -f docker-compose.production.yml \
  --profile routing --profile geocoding exec -T nginx sh -c \
  'if grep -Fq "try_files" /etc/nginx/conf.d/default.conf; then echo "SPA config"; else echo "gateway-only config"; fi;
   if test -r /usr/share/nginx/html/index.html; then echo "index mounted"; else echo "index missing"; fi'
```

If it prints `gateway-only config` or `index missing` **and the host build is present**, recreate
*only* the Nginx container with the VM overrides and existing local image; this leaves API,
Postgres, uploads and maps untouched. Do not omit the `-f` options or add `down -v`:

```bash
docker compose -f docker-compose.yml -f docker-compose.vm.yml -f docker-compose.production.yml \
  --profile routing --profile geocoding up -d --no-deps --no-build --pull never --force-recreate nginx
python3 scripts/vm.py doctor
```

If `/` still fails after that, or the config and mount were already correct, inspect the **status
and content-type only** with `curl -sS -o /dev/null -w 'HTTP=%{http_code} type=%{content_type}\n' \
http://127.0.0.1:8080/` (replace `8080` with your `NGINX_PORT`); report those values and the two
labels above. Do not paste `.env`, `docker compose config`, raw logs or tokens.

For a focused status snapshot (inspect/redact before sharing):

```bash
./scripts/vm-install.sh --check
python3 scripts/vm-map.py --show
docker compose -f docker-compose.yml -f docker-compose.vm.yml -f docker-compose.production.yml --profile routing --profile geocoding --profile production ps
python3 scripts/vm.py doctor
```

Do **not** send `.env`, `docker compose config` output, password values, raw dumps, tokens, or unsanitized logs to anyone. A diagnostic failure never authorizes deleting the database, upload evidence or map library. [Quickstart](./UBUNTU_VM_QUICKSTART.md) has exact operational commands; the long [VM runbook](./UBUNTU_VM_RUNBOOK.md) has manual recovery steps.
