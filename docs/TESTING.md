# Testing

The automated suite is Vitest with `@vue/test-utils`, `happy-dom` and V8 coverage, executed through Bun so the tests can import Bun-only modules (`bun:sqlite`, `Bun.password`, `Bun.serve`). There are no browser-driver dependencies, no separate mock server package and no old Python design tests. `bun run coverage` runs every `tests/*.test.ts` file and writes a summary report to `coverage/`.

Component, store and composable suites run in `happy-dom`. Server, realtime, script-mirroring and architecture suites declare `// @vitest-environment node` so they exercise the real Bun runtime without a DOM. The shared harness in `tests/helpers.ts` starts `createApp` with a `:memory:` database, an ephemeral port on `127.0.0.1`, deterministic admin credentials, demo seeding and disabled background jobs, and wraps same-origin fetch, session cookies, ticket issuance, WebSocket opening, JSON and binary message waiting and graceful shutdown.

## Suite structure

- `core.test.ts` checks validators, LRU and TTL behavior, token buckets, Argon2id password hashing, cookie helpers, geometry, offline SVG tiles, state machines and configuration.
- `api.test.ts` checks public health, OpenAPI, catalogs, the SPA shell, immutable SVG tiles, auth boundaries, saved places, shares, sync, tickets, SOS photo support, administrator CRUD, settings, audit and CSV exports.
- `auth.test.ts` checks registration, five security questions, onboarding, recovery challenges, one-use reset tokens, decoy challenges, logout and rotating refresh.
- `security.test.ts` checks CSP, CORS, frame ancestors, CSRF, request IDs, no-store headers, body limits, SQL-like input rejection, static path traversal, session revocation, rate limiting and preview-proxy forwarded-host CSP/CORS origins.
- `realtime.test.ts` checks one-use tickets, hello, ping, sync, room authorization, committed event publication, live-location fan-out, snapshot, one-to-one PTT floor control, ordered binary frames and malformed audio headers.
- `journeys.test.ts` checks complete requester, companion and administrator journeys plus a full login-to-rating journey.
- `smoke.test.ts` runs the in-process preview smoke against a `0.0.0.0` listener with simulated proxy headers, asserting the SPA shell, every precached asset, CSP/CORS/framing, tiles and SOS fan-out.
- `architecture.test.ts` checks the Bun-only toolchain, the absence of Node runtime imports and hand-authored JavaScript, the typed SFC/router/store surface, the shared protocol, animation policy, documentation, English-only Markdown and canonical design images.
- `assets.test.ts` checks the deterministic timestamp-free cache manifest, precache paths, Vite chunk shape, self-hosted fonts, the icon inventory, the design-token stylesheet and the compiled service-worker caching rules.
- `service-worker.test.ts` evaluates `public/sw.js` against mocked cache/network globals to verify install, activation, stale-while-revalidate, private-API bypass, bounded tile caching and offline fallback without a browser.
- `accessibility.test.ts` checks WCAG AA contrast for light-theme text and semantic colors, skip navigation, focusable landmarks, reduced motion, lazy view loading and keyboard palette behavior.
- `performance.test.ts` keeps validation, tile, concurrent-read, live-location and bundle-size budgets.
- `components.test.ts` mounts `AppToastHost`, `CommandPalette`, `LoginView` and `MapCanvas` with real Vuetify, Pinia and Vue Router plugins, and validates the 20-route table.
- `stores.test.ts` drives the auth, offline, map, SOS, realtime, admin and settings stores against mocked envelopes.
- `composables.test.ts` covers the settings tokens and theme cycling, the toast queue, `useAsyncAction`, the formatters, motion preferences, the SOS hold gesture and the command palette.
- `views.test.ts` mounts all 20 routed views and the layouts against a mocked API, then exercises the real route guard: anonymous visitors, both roles, onboarding, and the per-role landing route.
- `api-contract.test.ts` parses the interfaces in `src/client/api/types.ts` and checks each one against a real response from a running server: every required field must be present and carry the declared runtime shape. That file exists because nothing connected the hand-written view types to the serializers, and eight of them had drifted.
- `tests/setup.ts` is itself under test (`core.test.ts`, "test isolation"). It strips every key named in the repository `.env` so local settings cannot reach a suite — and `.env` sets `NODE_ENV=development`, so `NODE_ENV` must be pinned **after** that strip. Pinning it first let the strip delete it, which handed the decision to whatever the runner inherited: `test` under Vitest, but `production` after a build in the same shell. `loadConfig` then re-read the `.env` file and ran a different branch, and that was the only behavioural difference between this machine and CI.
- `motion.test.ts` treats motion as an accessibility contract rather than decoration: `prefers-reduced-motion: reduce` is how a user says animation makes them ill, so the preference has to reach every path. It pins the documented durations, the zero-collapse of both durations *and* movement (a 0ms duration still jumps), the GSAP timeline's own duration/stagger collapse, the empty-target guard that otherwise logs "target not found" on every load, and the shared motion-v presets staying inside the same budget (pinned in `composables.test.ts`). One honest limit is recorded in the test: the overview's `!reduced` guard before calling `revealTimeline` is behaviourally equivalent to passing `reduced` instead — both leave the card at its resting style — so the guard is a performance choice and no assertion can separate it.
- `realtime-store.test.ts` covers the session's single socket mirror, whose three load-bearing properties had never been asserted. The cursor must never move backwards — every reconnect resumes from it, so a stale value replays or skips events. `recentEvents` is capped at 40 and rendered in full, so it must drop the tail rather than grow one entry per server event. And `reset()` builds a fresh client, which is what stops a reconnect from delivering every event twice; it also intentionally drops domain listeners, because they belong to the session and the shell re-registers them. A store created outside an effect scope never runs `onScopeDispose`, so each test runs in its own scope.
- `companions-view.test.ts` covers who is sharing a position and for how long: peer names and accuracy, the fallback to a user id when no name is known, and live-versus-history shares including the "no expiry" case. It exists because the view was previously only mounted by the generic sweep, so how much of it executed depended on timing — see the note on thresholds below.
- `map-view.test.ts` covers the destination sheet: the four-place cap (beyond it the trip button is pushed off a phone screen), each quick chip actually recentring the map on the place its label names, the sheet expanding *and* collapsing again, and four-decimal formatting of a known fix. The store binds VueUse's geolocation when it is created, so a position stub must exist before the store and must call the success callback itself; `ownFix` is computed and cannot be assigned. Views do not start location — the map shell does — so a directly mounted sheet correctly stays on the permission prompt.
- `users-service.test.ts` covers saved places and mission readiness from the outside. The happy path was already covered; what was not is every way these endpoints can be reached with an id belonging to someone else. A saved place is private, so a foreign id answers 404 rather than 403 (which would confirm it exists), and a batch reorder containing one foreign id must roll back **completely** — a partial rewrite leaves the list in an order the caller never asked for. Also pinned: duplicate ids are refused, coordinates outside the map bounds and non-slug icons are rejected, and readiness is responders-only (a requester who could set it would appear available for missions they cannot accept). Server tests tear down with `close()`, not `stop()`.
- `app-shell.test.ts` covers the root component, which had no test at all. It picks the layout from `route.meta.layout` (falling back to `auth` for a route that declares none, so a new screen is never blank) and stamps the two attributes the stylesheet keys on: `data-mode` on `<body>` and `data-theme` on `<html>`. Missing either still renders, just with another layout's or another theme's rules. The global toast host and palette are asserted to sit outside the layouts. The layout swap is an `out-in` transition, so assertions on the incoming layout must wait a tick.
- `settings-view.test.ts` covers the operational switches. The PUT sends every row and the server validates the payload as a whole, so one malformed value — including one the administrator did not touch — rejects the whole save with a bare "Invalid request.". The three switches accept only `'0'`/`'1'` and the dispatch radius is 2-6 digits; the form names the offending key. Rows are labelled in words rather than by raw key, and a save neither wipes untouched values nor reports success when refused.
- `admin-layout.test.ts` covers the administrator shell, which is the only thing keeping the console live. Each realtime subscription is asserted to refresh exactly the slice its event invalidates (SOS created/dispatched → queue, alert → badge, settings → switches); dropping one fails a named test. The unresolved-alert count and the connection pill are pinned: it must read as reconnecting unless the socket is live, so a console never claims to be realtime while it is not. Sign-out is covered too. Note that removing the shell's explicit unsubscribe does *not* fail a test: `RealtimeStore.disconnect()` calls `reset()`, which already unsubscribes the same handlers, so that line is defence in depth rather than the only guard.
- `groups-view.test.ts` covers service-group management, which decides who can be dispatched. The creation payload requires at least one incident type for coverage, and that catalog is loaded in parallel with the list — so a failed catalog load used to make every submission fail with a message that never mentioned it. The form now names that cause, along with the name-length, `#RRGGBB` and capacity bounds the server enforces, all of which otherwise return a bare "Invalid request.".
- `mission-offers.test.ts` covers the offer contract end to end against a live server: one pending offer row per named responder plus `assigned_responder_id` only for the single-recipient case, `ready_only` refusal with the blocking user ids named, decline (twice = 404), Policy-A accept flipping readiness inside the transaction, Policy-B refusal at accept time (409), immediate dispatch (exactly one responder, `accepted` SOS + `assigned` mission, no offers, start transition mirrors onto the SOS), the job-types list/create/update endpoints, unknown-job-type rejection on user creation, and the nearest endpoint answering 404 for an unknown SOS id. Creation stays inside the emergency bucket by sharing one probe SOS.
- `job-types-view.test.ts` covers the job-types admin screen: catalog rows with policy and member count, the empty state, creating a job type, a server-side refusal surfacing in the form, and the two one-click mutations (policy flip, activation) sending the negated value.
- `users-view.test.ts` now also pins the responder-only job-type select: it sends the chosen `jobTypeId` on PATCH, and the account-creation form carries the selected job type for responders.
- `dispatch-view.test.ts` covers the dispatch board, which is the only screen that turns a pending SOS into a mission. The server rejects a dispatch outright when any named responder is not an active member of the chosen group, so the board must send `groupId` plus the group's own `memberIds`; it previously sent a hardcoded seeded demo id to `groups[0]`. Tests cover skipping memberless and inactive groups, refusing when no staffed group exists, surfacing a rejection instead of a success toast, and reloading the queue afterwards. It also pins the `loadDispatch` unwrapping: the endpoint returns list envelopes, not bare arrays.
- `onboarding-view.test.ts` covers the forced gate for administrator-created accounts: five slots render even before the catalog arrives, the five answers travel with the question chosen in the *same* slot (a positional shift would bind an answer to the wrong question and lock the user out of their own recovery), an incomplete form sends empty slots rather than a shorter array, and a refused submission leaves the form enabled. `VSelect` renders a `VTextField` of its own, so the helper filters to the five real answer fields.
- `users-view.test.ts` covers user administration: the activation toggle sends the negation of what the row shows (the payload field is `active`, not `isActive`), a refused toggle is reported rather than claimed as success, and the search term and role filter travel as query parameters. The account-creation form refuses a temporary password below the server's 12-character floor or missing a digit, before any request is made, and keeps the form on a duplicate-username conflict.
- `login-view.test.ts` pins `landingRoute` for every role and both onboarding states (onboarding wins over the role, or the guard bounces the redirect), then signs in against a fetch double: a trimmed lowercase username, a password that is never trimmed, the device name sent for the session list, and each failure kind left on the form with the button usable.
- `talk-view.test.ts` covers push-to-talk with a fake WebAudio graph: a press opens a turn and every release path closes it (`pointerup`, `pointercancel`, `pointerleave`, keyboard), a refused floor request releases the microphone instead of leaving the button live, unmounting mid-sentence stops every track, and an incoming frame is decoded without throwing.
- `register-view.test.ts` covers the two places a password is chosen: the shared `usePasswordPolicy` mirror of the server rule, and the registration form — submit disabled below five questions, mismatched passwords, a weak password, duplicate questions, a blank answer and a taken username all rejected before or at the network, with the form keeping what was typed.
- `sos-view.test.ts` walks the four-step composer with its catalogs loaded: severity and incident selection, forward and back navigation, the review card echoing the draft, adopting the device fix (and doing nothing when there is no fix), a successful send that resets the composer, and the pre-flight description check that stops a request the server would reject with an opaque message.
- `mission-view.test.ts` drives the responder screen against a loaded store: the rail built from the detail call, the single action the current status permits, the progress payload, a rejected transition surfacing as an error toast rather than a success, and the one-time rating form that only a completed, unrated mission shows.
- `admin-overview-view.test.ts` renders the reports and overview screens from a payload copied from `AdminService.overview()`, so `statusCounts`, the `{ day, count }` trend, `recentRequests` and the alert-count card are all exercised against the real key names.
- `profile-devices.test.ts` renders the device list from a payload copied verbatim from a live `GET /_user/devices` response, checks that the current session cannot revoke itself, and that another session is revoked by its `sessionId`. `api.test.ts` pins the same contract on the wire, including the 404 on a repeated revoke.
- `recovery-view.test.ts` walks the three-step recovery flow on its route: normalized username lookup, the three challenge answers posted against the returned `recoveryId`, the redirect back to login, identical handling of decoy challenges for unknown accounts, and recovery from a rejected answer or a rate limit without a stuck button. It also pins the client-side password policy, which stops a known-invalid secret from being posted for the sake of a bare "Invalid request.".
- `sos-store.test.ts` pins the emergency path: the five-endpoint load (catalogs, both lists and the offers list), the seeded incident type that survives a reload, the composer's clamped step cursor, the exact submit payload (photo only when attached), and that a failed submit keeps the draft so the user only has to press again while the `submitting` flag is still cleared.
- `command-palette.test.ts` types the real Ctrl+K / Cmd+K chord, filters, wraps the highlight with arrows, Home and End, checks that default scrolling is prevented, runs the active command, and mounts the dialog to assert focus, single-step arrow movement, role-aware entries, backdrop dismissal and the announced match count. Every command's label is also a promise, so `command effects` drives each one and asserts its *effect*: all six user destinations and all five administrator destinations (by the route each was given), that the theme command really changes the theme, and that refresh really reloads. Two harness facts: the router guard refuses `sos` and the `admin-*` screens for an anonymous session, so those tests sign in first; and a command's `run` calls `router.push` without awaiting it, which does not settle `currentRoute` under the test router, so assert the destination passed to `push`. Narrowing the list must also pull the highlight back inside it — without that the index points past the end of a shorter result set, nothing renders as selected and Enter runs nothing.
- `map-shell.test.ts` exercises the mobile shell as a behaviour: realtime subscriptions and their teardown, geolocation start/stop, the press-and-hold SOS gesture from pointer and keyboard (including cancellation), the offline banner, logout and Escape navigation.
- `talk-floor.test.ts` covers the server side of push-to-talk, which had no test of its own and is the one place where a wrong branch delivers audio to someone who should not hear it. Every refusal is asserted by its reason (`self-talk-is-not-allowed`, `participant-is-busy`, `not-the-speaker`, `talk-not-active`, `talk-expired`, `invalid-sequence`, `invalid-payload-size`) so a regression names the rule it broke: the listener cannot speak or hang up on the speaker, a replayed or non-integer sequence is refused, the payload ceiling is inclusive while the empty frame is not, a refused frame does not consume its sequence number so the next legitimate one is not mistaken for a replay, and expiry releases the floor instead of leaving both participants permanently busy. The sweep distinguishes idleness from expiry, ignores a speaker who is still sending, and `activeForUser` hands out a copy so lowering `lastSequence` on the snapshot cannot replay audio. Two arms in `talk.ts` stay uncovered deliberately and the file says why: `releaseUser`'s inactive branch and `sweep`'s skip both guard an invariant that `release()` maintains in one step, so reaching either would mean the invariant had already broken.
- `map-canvas.test.ts` mounts the map surface itself rather than the view around it, and exists because of a real defect: `MapCanvas.vue` carried its own copy of the Web-Mercator projection while `@shared/geo.ts` carried another, and the two had drifted — the shared one clamps latitude to ±85.05112878, the component's did not. At exactly ±90 degrees the y term becomes infinite, both tile loop bounds become infinite, and rendering never finishes. Restoring the old component makes this suite hang with no output, which is the assertion. The fix is to delete the copy and use the shared helper, so there is one projection and it keeps its clamp. The rest of the suite asserts the geometry the component actually publishes to the DOM: every marker sits at the coordinate the shared projection gives, to six decimal places; the tile grid is a complete rectangle inside the world bounds, clipped at the antimeridian instead of requesting tile -1; an incident marker appears only for a request that is still live, so a completed or cancelled incident cannot render as an active alarm; an empty place icon falls back instead of producing the class `mdi-`, which renders nothing at all; and a peer without a username is still labelled. `MapCanvas.vue` is at 100% of statements, branches, functions and lines.
- `offline-store.test.ts` covers the store that tells a responder in a basement whether the app is still talking to the network. The failure cases are the substance: the `data-offline` attribute must be applied immediately rather than on the next tick (a watcher without `immediate` leaves one frame of online-looking UI at start-up, which is exactly when it is being read) and must be *removed* when the connection returns, or the screen stays dimmed on a perfectly good network; the disconnect timestamp must record when the connection went down and not be overwritten when it comes back. Registration returns a boolean in every case — no worker support, a `file://` document, a rejected registration, and a `ready` that resolves to nothing all report failure without throwing, because offline support is an enhancement and must not take the app with it, and the root scope is asserted because a narrower one would leave the map routes uncached. `loadCacheVersion` asks for the manifest with `cache: 'no-store'` (a cached manifest reports the version the user is not running) and refuses a version delivered with an error status: a 404 carrying a JSON body would otherwise be parsed and the app would advertise a cache it never received. A transient failure must also not erase the version already displayed. Everything is created inside an `effectScope` so the listeners and watchers go away between tests.
- `websocket-hub.test.ts` drives `server/core/websocket.ts` — the hub every realtime frame passes through — directly with a fake Bun socket, because the end-to-end `realtime.test.ts` proves the happy path and nothing about the refusals. Close code checks: a code outside 1000-4999 is a protocol violation and browsers drop the connection, so the hub substitutes `INTERNAL` rather than pass it through; a close reason is truncated because the frame limit is 123 bytes. A peer closes exactly once — the second `close()` must not re-run disconnect cleanup or double-remove the room. Outbound frames over `maxFrameBytes` (boundary tested at exactly the limit) close the peer rather than throw into the caller, as does a socket that throws mid-send. Malformed JSON and non-object bodies are answered with an `INVALID_INPUT` frame instead of being silently dropped, which is what would look like a stalled app; a JSON array or a body without `type` gets the same treatment. Handlers that throw or reject are caught, reported to the peer as `INTERNAL`, and never close the connection — one bad handler must not cost the responder their call. Room names are restricted to `[a-z0-9:_-]{1,80}` rather than sanitised, and a peer is capped at 32 rooms; joining the same room twice is a no-op. `user:`, `session:` and `role:` rooms are indexed case-insensitively so an audience built with different casing still reaches its members. The heartbeat closes a peer that neither pongs nor sends within one interval, and every socket is closed with `GOING_AWAY` on shutdown. Everything runs with fake timers, in isolation from the real server.
- `config.test.ts` covers the production-safety and trust-parsing branches of `server/core/config.ts`: boolean-ish environment values parse case-insensitively, `PORT` rejects non-integers and out-of-range values, `ALLOWED_ORIGINS` is trimmed and de-emptied, the production guards refuse unsafe admin passwords and demo seeds, forwarded proto/host are honoured only from a trusted proxy (a garbage proto is dropped), a missing host falls back to `localhost:<port>`, `*` in an origin pattern matches anything, a suffix wildcard respects the dot boundary and cannot swallow the apex or an attacker-suffixed host, regex metacharacters in patterns are escaped, and the client-IP resolver prefers the first forwarded address only from a trusted proxy and strips the IPv4-mapped prefix. The `.env` read path and the repository-root resolver are deliberately untested: under `NODE_ENV=test` the environment is `process.env` as-is, and covering them would make the suite depend on the checkout.
- `shared-geo.test.ts` pins down the one module shared by the Bun server and the Vue client with exact, checkable properties rather than smoke assertions: poles clamp instead of producing NaN/∞ (sin 90° is 1 and log of ∞ is indeterminate, so the clamp is load-bearing), antimeridians land on the scale edges, haversine reproduces a known intercity distance, bearings hit the cardinal points (89.85° due east is the *correct* great-circle answer, not a bug), the stale-fix policy rejects NaN, history and >5s future skew, and the Persian display helpers zero-pad and fall back to an em-dash rather than emit `NaN` or `undefined`.
- `map-store.test.ts` covers the map store's failure paths, which are where a blank map hides: an API failure surfaces the server's localized message (the transport normalizes even a raw string throw into an `ApiError`), a configuration without center or zoom keeps the canonical Tehran defaults, a missing `items` array decodes to an empty list, a fix without usable accuracy reports 25 m — never 0 m, which would read as survey grade — a missing heading or speed reports `null` rather than `NaN`, a zero latitude reads as no fix, saved places are rank-ordered with in-place replacement, a double delete is tolerated, and the geolocation watch is started and stopped through the real vueuse watcher (`watchPosition`/`clearWatch` are asserted on a stubbed browser API). The stores no longer hand-roll a non-`Error` fallback in their catch clauses: they route through the shared `errorMessage()` helper, so there is no store-specific dead arm left behind, and `errorMessage()`'s own non-`Error` fallback (the transport normalizes even a raw string throw into an `ApiError`, and a rethrown AbortError is an `Error` subclass in every supported runtime) is covered by the api-client suite instead.
- `realtime-client.test.ts` drives the browser transport with a fake socket (ticket request, queueing, heartbeat, durable cursor, reconnect policy, binary routing) and the push-to-talk codec with a fake Web Audio context.
  A second block extends it to the failure paths, because the transport is where a connection quietly dies: a throwing listener must not take down the others on the same channel, a connect already in flight or already closed must be refused, every durable event channel is subscribed exactly once, `wss:` is used when the page is HTTPS, a socket error surfaces as a status and not a crash, a message that is neither string nor buffer is dropped rather than JSON-parsed as `[object Blob]`, a hello without `eventCursor` or a ticket without `heartbeatMs` falls back to sane defaults instead of `NaN`, an event without an id never moves the cursor backwards, two close frames schedule a single reconnect timer (observed via `getTimerCount`, not via the wall clock), a dead TCP write reports `false` rather than throwing, and `sync()` defaults to the current durable cursor.
- `acceptance.test.ts` checks the closed target checklist, legacy scope reconciliation, release evidence, Bun automation scripts and CI coverage.
- `database.test.ts` verifies the idempotent migration for older SQLite databases and the production configuration guards.

## Commands

Run one suite while iterating, for example `bunx --bun vitest run tests/realtime.test.ts` or `bunx --bun vitest tests/components.test.ts` for watch mode. Run `bun run coverage` for the whole suite with coverage, `./boro check` for the full gate (build, both typechecks, documentation guard and coverage) and `./boro verify` to add runtime diagnostics. `bun run bench` records release latency figures, `bun run smoke` runs the reproducible in-process runtime smoke and `bun run acceptance` validates the checklist and evidence. None of these commands performs browser-driven professional UI acceptance.

Coverage thresholds (94% statements, 95% lines, 94% functions, 83% branches) are set below the *worst* figure the suite produces, not below a single measurement, and that rule has now cost a red build twice.

The first time, two map views were only ever mounted by the generic "every view mounts" sweep, so how much of them executed varied with timing and the total moved between identical runs (87.06-87.32%). Both have deterministic suites now.

The second time is what shaped where the guards sit today. Several spec files import the same single-file component — the generic sweep mounts `MissionView.vue` and `mission-view.test.ts` drives it — so the component is instrumented more than once with different statement ids. When the v8 remap merges those records it reports one of them rather than their union, and which one it keeps is not stable. `MissionView.vue` therefore reports 45 or 43 covered lines from run to run, which moved the total by a tenth of a point. Three remedies were measured and none removed it: `fileParallelism: false`, `experimentalAstAwareRemapping: true`, and importing the components statically instead of through a computed specifier. The effect is whole-file: in a low run the file's uncovered set is `{30, 47, 49, 55, 65}`, and in a high run it is `{56, 57}` — the two sets are not nests of each other, which is what rules out a union and rules out a genuinely flaky test. So the guards sit below the *lowest* figure seen in the closest emulation of CI — a fresh worktree with a real `bun install --frozen-lockfile`, `bun run assets` and `bun run build` — which measured 90.02 / 93.43 / 89.86 / 77.84 across runs. After the suite grew further, the guards were raised again, to the current 94 / 95 / 94 / 83 stated above. A symlinked-modules checkout reported 90.24% functions and hid the remap flap that cost one red build. A threshold between the two figures would be a coin flip, and that is exactly how the last red build happened.

One practical consequence: measure coverage the way CI does, in a fresh checkout that has run `bun run assets` and `bun run build`, and never from a threshold set on a single local run. They exist to catch silent regressions, not to certify the product. Generated output, the service-worker artifact and the process entry point are excluded.

## Interpretation

A failure in an API or journey test usually indicates a route, service or state-machine regression. A realtime failure can indicate an event publication, ticket, room or binary-frame regression. An asset failure usually means the generator must be rerun or a view stopped using a shipped icon. An architecture failure means a boundary, documentation or toolchain invariant was broken. Professional visual acceptance against the canonical PNG references remains a separate review activity and is not part of this automated suite.
