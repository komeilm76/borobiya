# Security

Security is enforced at the HTTP boundary, the session layer, the service layer and the browser. The runtime is Bun itself plus a generated browser bundle, so the trusted server surface is small and auditable. Private APIs are never cached by the service worker, and browser code contains no API keys or external script sources.

## HTTP defenses

Every response receives a strict Content Security Policy: scripts and workers are same-origin, styles are same-origin plus the small inline style allowance required by generated components, images are same-origin or data URLs, and WebSocket connections are limited to the calculated same-origin `ws` or `wss` endpoint. When `TRUST_PROXY=1`, the endpoint is derived from `X-Forwarded-Proto` and either `X-Forwarded-Host` or the request `Host` header, so a preview or reverse-proxy origin receives its own `wss://` value. Frame ancestors are denied by default. Set `FRAME_ANCESTORS` to an explicit comma-separated list of CSP source expressions when the app is embedded by a trusted preview or dashboard; in that case the legacy `X-Frame-Options: DENY` header is omitted so it cannot conflict with the CSP allowlist. Production checks reject wildcard frame ancestors. Other headers disable content-type sniffing, set referrer policy, apply cross-origin isolation and add HSTS in production.

CORS is explicit. Same-origin requests are allowed without an `Origin` header. Requests with an origin receive credentialed CORS headers only when the origin equals the calculated same origin or matches `ALLOWED_ORIGINS`. Mutating requests additionally pass an origin check before parsing. `Sec-Fetch-Site: cross-site` is rejected unless the origin is explicitly allowed. Do not configure wildcard origins with credentialed cookies.

## Input and rate limits

Bodies are bounded by `MAX_BODY_BYTES`; declared and streamed sizes are checked before parsing. All JSON bodies and query strings use strict schemas that reject unknown fields. Numeric ranges, identifier patterns, enum values, coordinates and data URL formats are validated before services run. Rate buckets protect authentication, recovery, tickets, ordinary mutations, emergency actions, realtime location, talk starts and audio frames. A 429 response includes `Retry-After`.

WebSockets have a maximum frame size, heartbeat timeout, room limit and typed close codes. One-use tickets are random, hashed at rest, short-lived and IP-bound. Audio frames are checked for version, type, active talk floor, speaker identity, sequence order and payload size before forwarding. Only the intended peer receives a frame.

## Accounts and sessions

Passwords are chosen under a strict policy (12–128 characters, letters and numbers) enforced at registration, recovery reset and administrator-created accounts. Sign-in accepts any provisioned secret, so bootstrap credentials supplied by an operator still work. Passwords and security answers are hashed with Argon2id through `Bun.password`, which uses a per-value random salt. Answer normalization is consistent before hashing, and stored hashes are self-describing so the algorithm can be upgraded later. Unknown users follow a dummy-hash path during login, and unknown recovery usernames receive a decoy challenge with the same visible shape. Failed logins increment a counter and can temporarily lock the account. Recovery challenges have attempt limits, expiry and one-use reset tokens. A successful reset revokes every session and disconnects realtime peers.

Sessions use `HttpOnly`, `SameSite=Lax`, path-scoped cookies, optional secure cookies, IP binding, expiry, refresh rotation and revocation. The server stores a hash of the session secret. Deactivating a user revokes all sessions. The last active administrator cannot be removed, and an administrator cannot suspend or demote their own active account.

## Data protection

SQLite uses foreign keys, prepared statements and forward-only idempotent schema migrations (v8 adds mission teams; v9 adds the consented track tables `track_points`, `track_consents` and `track_summaries` plus `users.record_track`, default OFF). Audiences on durable events restrict catch-up and socket publication. Ambient location history requires an active authorized share. Consented trip/mission tracks are stored separately and are retrievable only by context participants, by window-covering history-share recipients under the grant's scope projection, or by an audit-logged administrator; raw points are purged in batches after the configurable retention (`TRIP_TRACK_RETENTION_DAYS`, default 180), after their summaries have been persisted. Audit CSV escapes spreadsheet formulas. Production startup rejects known bootstrap, demo, preview and CI passwords, passwords shorter than twelve characters and enabled demo seeding. `./boro deploy:check` also requires `COOKIE_SECURE=1`, `TRUST_PROXY=1` and exact non-wildcard allowed origins behind HTTPS. Audio is ephemeral and is never stored.
## Authorization audit (Stage 7)

An inventory of every declared route (`src/server/routes/index.ts`, 107 registrations) against the OpenAPI document, the session layer and the service guards:

- **14 public routes** (`auth: 'none'`), exactly the ones that must be reachable without a session: the seven `/_public/*` readers (health, OpenAPI, the three catalogs, map config, SVG tiles) and the seven `/_auth/*` entry points (register, login, refresh, logout, recovery start/answers/reset). Every other operation in `/_public/openapi.json` carries `security: [{ sessionCookie: [] }]`; the document does not claim an anonymous path that the router would deny.
- **53 user routes** (`auth: 'user'`): every one resolves the caller from the session and either scopes to the caller's own rows or to an explicitly shared resource. Unknown or foreign resource ids answer **404, never 403** — SOS detail, trips, saved places, location history, devices, sessions and support-requests all follow this rule, so existence is never confirmed across accounts. Membership or role failures (a non-member trip roster, a non-leader action, another member's support request) answer 403 where the caller's role is known but insufficient.
- **40 administrator routes** (`auth: 'admin'`): the console, dispatch, reports, users, groups, job types, incidents, audit, alerts, settings, health, mission rosters, support-request review and team dispatch. Administrator-only facts (removal reasons, internal review notes, full user projections) never leave this surface. The last active administrator cannot be removed, and an administrator cannot suspend or demote their own active account.
- **Every mutating route declares a rate bucket** (`RATE.*`); no `POST`/`PATCH`/`PUT`/`DELETE` is unthrottled. Anonymous buckets guard auth and recovery; emergency actions, tickets, ordinary mutations, location, talk starts and audio frames have their own limits.
- **Ownership evidence** is enforced and tested: foreign saved-place/place ids answer 404 and batch reorder rolls back completely (`users-service.test.ts`); SOS/mission visibility and transitions, collection masking and group-vs-offer fallback (`sos-guards.test.ts`); location share creation/revocation and history scoping (`service-guards.test.ts`, `location-flows.test.ts`); administrator account, group, membership, settings, audit and CSV-injection guards (`admin-guards.test.ts`); mission team roles, leader designation, member removal and support-request review (`mission-teams.test.ts`, `mission-team-panel.test.ts`, `mission-offers.test.ts`); trips leader/member authorization and invitation acceptance (`trips.test.ts`); track recording gates, per-context consent, share-scope replay, the fail-closed purge and the audit-logged administrator read (`track.test.ts`, `track-store.test.ts`, `track-components.test.ts`).

Residual risks accepted for 2.0.0: a session cookie does not bind to a device fingerprint beyond IP binding; ambient location history (the live-location feed, as opposed to the consented trip/mission tracks) outside an active share is not retrievable at all — there is deliberately no "my trail" endpoint for it; consented tracks persist GPS fixes for up to `TRIP_TRACK_RETENTION_DAYS` (default 180) and are purged in batches by the maintenance job, but a stolen session with an opt-in history can expose recent recorded points until the session is revoked; and there is no audit export retention period enforced by the runtime (retention is an operations decision, see `docs/OPERATIONS.md`).
