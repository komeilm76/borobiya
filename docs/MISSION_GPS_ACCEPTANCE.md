# Private mission GPS — field acceptance checklist

This is a **manual acceptance plan**, not a record of a completed device run. The source-level and migrated-database tests do not establish operating-system permission behavior, background delivery, map rendering, or accuracy of a real GPS receiver. Record device/build/OS/browser, network state and pass/fail evidence for each scenario before signing off. Use dedicated test accounts and a non-emergency test incident; never paste precise private coordinates, tokens or account credentials into an issue.

## Setup

- Use the documented HTTPS phone/LAN setup or a deployed same-origin site with migrated database and working Socket.IO, map tiles and route service. Confirm the test device can grant location permission. Record whether the client is a browser tab or the native shell; repeat critical scenarios for each supported target.
- Prepare one requester, two available rescuers, one admin and one unrelated user. Create **two accepted, simultaneously active assignments** for the requester (one per rescuer); record only the test mission IDs in private QA evidence. Leave general Broadcast off for everyone.
- Start from fresh logins and a clean mission history. Arrange an observable walking/vehicle route in a safe environment; suggested route comparison is a preview, not turn-by-turn proof or a speed/arrival measurement.

## Checks (mark each pass/fail with evidence)

1. **Search and room on phone/desktop:** Search for enough places to overflow the card. Scroll results with touch, wheel and keyboard: the results scroll inside the card, while the map remains available; reopening on a phone must not create a second competing scroller. Open and close “اعضای مأموریت” on short phones, large screens, light/dark themes and with a screen reader. Verify that the compact card stays fixed while only its member-profile list scrolls, its close button remains reachable, and clicking or keyboard-activating any fresh authorized member row centers the map without stealing route/GPS-follow intent. Stale, missing and withdrawn positions must not focus; try a revocation while the card is open. Verify status, map buttons, RTL order and safe-area clearance without tiny tap targets. Confirm that the admin's recipient/privacy settings remain outside the member card and that connection/GPS recovery warnings remain reachable. Trigger a search service error: the primary advice should be understandable to a user; the technical report remains in its expandable support section.
2. **Mandatory private sharing:** With GPS permission and network available, verify that the requester publishes to **both** active missions and each rescuer to their own mission without opening the map panel or enabling general Broadcast. Check distinct member locations for the appropriate mission. Do not mistake a connected-room badge for a fresh GPS fix. Confirm there is no participant disable switch and no public Broadcast change.
3. **Default and recipient-specific admin sharing:** Before any admin action, verify admin GPS is not published. Save one admin recipient, deliberately start admin sharing, then verify only that recipient sees the admin fix; repeat for the other recipient and both. Stop admin sharing. Test independent rescuer→requester and requester→rescuer visibility toggles, including revocation of a marker already shown. The admin must retain access to both participants. The unrelated account must not subscribe, read policy, see live fixes or read completed traces. Check behavior from a second tab/device, not just the admin's own map.
4. **Denial, outage and terminal boundaries:** Deny GPS permission, disconnect the network, refresh/reconnect, switch accounts and complete/cancel an assignment. Confirm warnings or stale indicators rather than invented fresh positions; watches and markers must stop at logout/terminal state. After one assignment ends, the requester's other active assignment must continue; after a failed verification, sharing must fail closed until verified. Browser/OS suspension may stop callbacks: **do not pass** a claim of uninterrupted background tracking based on a foreground test.
5. **Recorded history and route comparison:** During a real test trip, start guidance after explicitly selecting a route; note selection time. Complete the mission and open the collapsed history as each permitted participant and admin. Compare recorded per-role sample timestamps/accuracy with device observations; look for gaps across outages, not invented straight lines. The rescuer comparison should use samples from the last saved route selection onward, while colored traces show the whole recorded mission. Repeat with rescuer visibility disabled (requester must not see the rescuer trace or selected route), with a route-save failure (no invented preview), and with no GPS permission (no fabricated path). Check that an unrelated account and a still-active mission cannot read the completed trace endpoint. Lengths are sample-based estimates, not a complete odometer.

## Sign-off

For each target device/build, record the date, tester, environment, the five checks above, any failed step and reproducible conditions. If OS time, GPS accuracy or connectivity is unreliable, explicitly note the limitation rather than accepting the trace as a complete journey. Keep this checklist open until actual device evidence exists; automated tests and browser mocks are supplementary only.
